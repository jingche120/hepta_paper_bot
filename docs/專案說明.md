# 每日推薦論文 bot：這個專案在做什麼

> 這份文件說明**為什麼**與**怎麼運作**。實際的安裝與執行指令請看 [README.md](../README.md)。

## 一句話

把你在 Heptabase 寫的論文筆記當成「你的研究興趣」，每天自動從 arXiv 撈新論文，
挑出跟你興趣最接近的幾篇，寄到你信箱。

## 要解決的問題

arXiv 每天有上百篇新論文湧入。以你訂閱的三個類別為例：

| 類別 | 新論文 |
|---|---|
| `physics.geo-ph` | 約 1.7 篇/天 |
| `eess.SP` | 約 16 篇/天 |
| `stat.ML` | 約 15 篇/天 |

人工掃過標題不但花時間，而且**標題常常看不出這篇跟你的題目有沒有關係**。
真正能判斷相關性的是摘要，但沒有人每天讀三十篇摘要。

這個 bot 的作法是：**用你已經讀過的論文當基準**，讓機器算語意相似度來排序。
你讀過的論文本身就是你興趣最準確的描述，不需要你另外維護關鍵字清單。

## 怎麼運作

```
Heptabase 白板「讀過的論文總覽們」
        │
        │  ① get_hepthabase_bot.py --export
        │     逐張讀卡片 → 抽出摘要與關鍵字
        ▼
data/reading_history.json  ← 你的閱讀紀錄（比對基準）
        │
        │  ② main.py
        ▼
   ┌──────────────────────────────────────────────┐
   │ arXiv 當日新論文 + IEEE 期刊增量 → 存進候選池 │
   │            ↓                                  │
   │ 只對還沒有向量的論文算 embedding              │
   │            ↓                                  │
   │ 對池中所有未讀論文評分（質心 × 時間衰減）      │
   │            ↓                                  │
   │ 依配額取 n_new 篇新的 + n_old 篇舊的          │
   │            ↓                                  │
   │ 抓全文 → LLM 產生 TLDR → 寄信                │
   │            ↓                                  │
   │ 記錄推薦次數（輪替用）                        │
   └──────────────────────────────────────────────┘
                     ↑
          data/paper_pool.sqlite ← 候選池（arXiv + IEEE，含向量）
```

### 為什麼分成兩步

讀 Heptabase 需要 OAuth 瀏覽器授權，推薦流程則要能排程、能離線重跑。
綁在一起的話，授權一過期整條流程就掛掉。

拆開之後：閱讀紀錄是一個本地 JSON 檔，推薦流程只依賴這個檔案。
你可以反覆調整類別、重跑排序、除錯，完全不需要再碰 Heptabase。
只有在你新增了論文筆記時，才需要重跑步驟 ①。

## 三個核心概念

### 1. 閱讀紀錄（reading history）＝ 你的興趣

每筆閱讀紀錄是 `CorpusPaper(title, abstract, added_date, paths)`。
關鍵在於 **只有 `abstract` 會被拿去算相似度**。標題完全不參與計分。

所以卡片裡摘要寫得好不好，直接決定推薦準不準。
這也是為什麼卡片格式要求 `## English Abstract` 與 `## 中文摘要` 兩個章節，
而方法概覽、實驗設定、主要結果那些章節會被**排除在閱讀紀錄之外** ——
把實驗數據混進去只會稀釋語意訊號。

英文摘要要保留原文，因為比對的對象是 arXiv 的英文摘要，同語言訊號最強；
中文摘要則補上你自己關注的角度。

### 2. 相似度排序

把候選論文和閱讀紀錄的摘要都轉成向量，算餘弦相似度。
每篇候選論文對「所有閱讀紀錄」各算一個分數，再加權平均成單一分數。

目前走 OpenAI 的 `text-embedding-3-small` API。
也可以改用本機模型（`executor.reranker: local`），完全不花錢，但要裝 torch（數百 MB）。

### 3. 排序後才抓全文

論文全文（LaTeX 原始檔或 PDF）只有產生 TLDR 與作者單位會用到，
而那只需要選中的那 3 篇。

上游的做法是**先對所有候選論文抓全文，再排序** —— 把整天的論文下載下來，
然後丟掉九成。實測單篇下載解析要 14～56 秒，178 篇候選就是兩個多小時。

本專案改成排序之後才抓：

```
上游：檢索 → 抓 178 篇全文 → 排序 → 取前 N 篇 → TLDR
本專案：檢索 → 排序 → 取前 N 篇 → 抓 N 篇全文 → TLDR
```

實測以 178 篇候選、選 2 篇驗證，下載量減少 99%。
候選論文的排序只讀摘要，所以這個順序調換不影響推薦結果。

### 4. 候選池（v2 的核心）

v1 的候選論文用完即丟：每天檢索、排序、寄信，然後全部丟棄。
今天沒讀完的推薦，明天就消失；2022 年以來的相關論文也從未進入視野。

v2 把所有檢索到的論文存進 `data/paper_pool.sqlite`，每天從**整個池子**挑選：

- **配額**：`pool.n_new` 篇新論文 + `pool.n_old` 篇池中舊論文，預設 2 + 1。
- **輪替**：排序鍵是 `(推薦次數 ASC, 分數 DESC)`。推薦過的排到隊伍後方，
  等其他高分論文輪過一遍才再出現，所以不會連續多天重複同一篇，
  但也沒有論文會被永久丟棄 —— 只有寫成卡片才會被排除。
- **向量快取**：只對還沒有向量的論文呼叫 API。少了這層，每天要重算整個池子。

### 5. 時間衰減

閱讀紀錄依卡片建立時間排序，越新的權重越高，權重是 `1 / (1 + log10(排名 + 1))` 正規化後的值。

用意是：你半年前讀的論文跟現在讀的，反映的興趣強度不一樣。
最近在看的主題應該主導推薦結果。

這也是為什麼卡片**不需要手寫建立日期** —— Heptabase 的 `list_cards` 本來就回傳 `createdAt`。

## 專案結構

分成兩層，刻意隔開：

### 專案根目錄 —— Heptabase 這一側

| 檔案 | 職責 |
|---|---|
| `get_hepthabase_bot.py` | 進入點。連線、列出卡片、`--export` 匯出閱讀紀錄 |
| `heptabase_oauth.py` | OAuth 授權流程與瀏覽器回呼 |
| `heptabase_keychain.py` | 把權杖存進 macOS 鑰匙圈 |
| `heptabase_cards.py` | MCP 讀取：分頁讀卡片、列舉白板卡片 |
| `heptabase_reading_history.py` | 解析卡片章節、產生／讀取閱讀紀錄。純函式，不連網 |
| `paper_pool.py` | 候選池：SQLite 儲存、去重、評分、輪替選取。不連網 |
| `openalex.py` | IEEE TGRS / GRSL 來源（不在 arXiv 上，OpenAlex 免費且有摘要） |
| `embeddings.py` | 向量計算，回填與每日流程共用 |
| `backfill.py` | 一次性回填 CLI，按季分段、可續跑 |

### `src/zotero_arxiv_daily/` —— 推薦引擎

這是 [TideDra/zotero-arxiv-daily](https://github.com/TideDra/zotero-arxiv-daily) 的複製，
**刻意維持原樣**（不重新命名、不重排格式），這樣日後才能跟上游比對合併。
ruff 也把這個目錄排除在檢查之外。

我們只改了必要的部分：

| 改動 | 原因 |
|---|---|
| `executor.py`：`fetch_zotero_corpus` → `fetch_reading_history` | 換資料來源。這是整個替換的核心，其餘檢索、排序、寄信一行未動 |
| `utils.py`：`glob_match` 加相容層 | 上游用了 `glob.translate`（Python 3.13 才有），本機是 3.12 |
| `arxiv_retriever.py`：加 `lookback_days` | 選用功能，一次抓多天。預設關閉 |
| `arxiv_retriever.py` + `base.py` + `executor.py`：全文改成排序後才抓 | 見上方「排序後才抓全文」 |
| `executor.py`：`run()` 改走候選池 | 見上方「候選池」 |
| `base.py`：新增 `published_date()` | 池子要靠發表日區分新舊論文 |
| `main.py`：`config_path` 改絕對路徑 | 由根目錄的 `main.py` 啟動時，Hydra 會把相對路徑當成模組路徑而失敗 |

### 其他

## 已知限制與取捨

**每天執行，不是每週。**
`lookback_days` 可以一次抓多天，實測抓 7 天會得到 178 篇。
每天跑、每次只處理當日公告，量比較穩定。

**IEEE 期刊的論文都會被歸為「舊」，而且沒有真正的增量可用。**
OpenAlex 中這兩本期刊的 `publication_date` 是期號日期，實測 2026 年的論文
（兩本各抽樣 200 篇）**全部**標成 `2026-01-01`。所以它們永遠落在 `n_old` 那一側，
`n_new` 的名額實務上都由 arXiv 當日論文取得。

同樣因為這個粒度，`from_publication_date:yesterday` 會回傳 0 筆且不報錯；
而 OpenAlex 唯一能表達「最近新增」的 `created_date` / `updated_date` 過濾
**需要付費方案**（免費金鑰收到 HTTP 429 與 `Plan upgrade required`，
狀態碼像速率限制，實際不是）。因此每天改成重抓整個當年度，靠池子去重：
TGRS 約 10 次請求、GRSL 約 4 次，寫入的只有真正新增的那幾篇。

附帶好處是：OpenAlex 對**當年度**論文的摘要覆蓋率偏低（2026 年只有 48–61%，
2022–2025 年則是 99–100%），缺摘要的會先被略過；等 OpenAlex 補上摘要，
下一次重抓就會自動把它們撿回來。

**已讀論文的比對是模糊的標題比對，而且多數卡片本來就比對不到。**
`mark_carded()` 用正規化標題比對池中論文；比對不到的卡片會在 log 中列出。

實測目前 5 張卡片**全部**比對不到，這是正常的：它們的論文在
*Geophysical Journal International*、*SRL* 等期刊，不在回填範圍（arXiv `physics.geo-ph`
＋ TGRS ＋ GRSL）內，因此本來就不在池中，也就不會被推薦。

只有當那篇論文**確實在池中**卻比對不到時才需要處理——例如
`論文總覽：PatchTST` 的 `來源論文：` 指向 arXiv 查詢網址，卡片標題因此不是論文名。

**舊候選池會在開啟時自動升級。**
早期版本的 `norm_title` 索引不是 UNIQUE，`normalize_title()` 的規則也不同。
`open_pool()` 會重算標題、移除重複（保留狀態最完整的一筆）、把索引升級成 UNIQUE，
並把做過的事寫進 log。刪掉的是同一篇論文的另一個版本，內容重複。

**MCP 回應是純文字不是 JSON。**
`list_cards` 回傳的是 `card "標題" [uuid] created: ISO` 這種人類可讀格式，
靠正規表達式解析。若 Heptabase 改了措辭，列舉會**靜默回傳零張卡片**而不是報錯。

**沒有 API 金鑰也能跑。**
`generate_tldr` 與 `generate_affiliations` 都有 try/except 回退：
呼叫失敗時 TLDR 顯示原始摘要、作者單位留空，流程照常跑完寄信。
方便是方便，但也表示**金鑰設錯時不會有明顯錯誤**，只會發現 TLDR 變成了摘要。

## 成本

以每天推薦 3 篇計算：

| 項目 | 費用 |
|---|---|
| 回填 19,200 篇的向量 | **$0.15 一次性** |
| 每日 embedding（只算新進的數十篇） | 約 $0.0003 |
| 每日 TLDR + 作者單位（3 篇 × 6,000 tokens） | 約 $0.003 |
| **每月** | **約 $0.1** |

成本幾乎全在 TLDR：每篇論文送兩次 LLM 請求（TLDR 截斷到 4,000 tokens、
作者單位截斷到 2,000 tokens）。Embedding 的錢可以忽略。

**控制成本的旋鈕是 `pool.n_new` + `pool.n_old`** —— 它們決定郵件篇數與 LLM 呼叫次數。
向量快取（`pending_embeddings` 只回傳缺向量的列）是另一個關鍵：
少了它，每天要重算整個池子，成本會從每月 $0.1 變成 $4.5。

## 日常操作

```bash
# 新增論文筆記後，更新閱讀紀錄
.venv/bin/python get_hepthabase_bot.py --export

# 回填歷史論文（一次性；--embed 會呼叫付費 API）
.venv/bin/python backfill.py --embed

# 跑一次推薦，只印出選中的論文、不寄信
.venv/bin/python main.py executor.dry_run=true

# 改設定：編輯 config/custom.yaml，或用命令列臨時覆寫
.venv/bin/python main.py executor.debug=true
```

## 想讓推薦更準，先做這件事

**多寫幾張卡片。** 目前閱讀紀錄只有 5 篇。閱讀紀錄太少時，時間衰減權重形同虛設，
推薦會過度集中在少數幾個主題，也容易被單篇的用詞偏好帶偏。

寫卡片時，摘要寫完整（3～6 句以上），英文原文與中文理解都放進去。
這比調任何參數都有效。
