# 部署方案評估：Windows vs. ChatGPT / Grok 自動化平台

> 撰寫於 2026-09-09。文中關於 OpenAI / xAI 產品的描述來自公開資料（見文末來源），
> 這類產品變動很快，付費或簽約前請自行覆核。

要讓推薦流程每天早上 09:00 自動執行一次，評估過三類 AI 工作流程平台與一台 Windows 電腦。
**結論：Windows + 工作排程器明顯較簡單可行**，實作見 README 的〈每日排程〉。

| | Windows + 工作排程器 | Grok Bot | ChatGPT（各形態） |
| --- | --- | --- | --- |
| 技術可行性 | 可行 | 理論可行 | 不可行 |
| 月成本 | 0 | 約 US$200 | — |
| 每日執行的確定性 | 完全確定 | 由 LLM 代跑，不確定 | — |
| 160 MB 候選池 | 直接複製 | 要上傳，且無法自行匯出 | 無持久化檔案系統 |
| 失敗時能否除錯 | 可以，log 在本機 | 困難，環境不透明 | — |

關鍵認知：**這些 AI 平台不會省掉任何一項移植工作。** 仍然要裝 Python、裝依賴、
搬 160 MB 資料庫、重做一次 Heptabase OAuth。它們只是把「誰按下執行鍵」從排程器
換成一個 LLM —— 換來的是更高的成本與更不可靠的觸發機制。

## 一、決定可行性的五個硬條件

這不是一段提示詞，而是一支有狀態的批次程式：

| # | 條件 | 事實 |
| --- | --- | --- |
| 1 | 有狀態的資料庫 | `data/paper_pool.sqlite`：17,922 篇、160 MB，每天讀寫。是累積資產，不是快取。 |
| 2 | 真實的 Python 環境 | Python 3.12 + `requirements.txt` 17 個釘版套件，含原生 wheel（`pymupdf4llm`、`pymupdf-layout`、`numpy`、`tiktoken`）。 |
| 3 | 長時間執行 | 每天排序後逐篇下載並解析全文 PDF/tar，約 10 分鐘等級。 |
| 4 | 確定性 | 檢索 → 去重入池 → embedding 排序 → 選 `n_new` 新 + `n_old` 舊 → 寄信。每天必須套用同一套規則。 |
| 5 | 無法自動化的互動步驟 | `get_hepthabase_bot.py` 走瀏覽器 OAuth，權杖存在作業系統憑證儲存。**任何平台都無法無人值守完成。** |

第 5 點的推論很重要：**不管選哪個方案，都需要一台你能坐在前面完成授權的電腦。**
「完全不要本機」這個前提本身就不成立。

## 二、資料庫是最顯眼的症狀，不是病根

1. **這 160 MB 幾乎全是 embedding，重算要花錢。** `papers.embedding` BLOB 佔絕大部分體積
   （17,922 篇 × 每篇約 6–12 KB）。搬遷必須整份複製，不能到新機器重建。
2. **它每天變大，且必須讀寫同一份。** `pool.n_old` 每天從池中撈舊論文，靠
   `recommend_count` / `last_recommended_at` 輪替。若執行環境每天給一個乾淨的檔案系統，
   這個功能等於消失，**而且不會報錯**，只會默默推薦重複的東西。
3. **真正的病根是「有狀態的長期程式 vs. 無狀態的聊天執行環境」。** 同一個病根還會表現成：
   套件裝了明天不見、OAuth 權杖存不住、log 拿不回來。所以「把資料庫換成雲端 Postgres」
   解不了題 —— 後面還有四個一樣的洞。

## 三、逐平台評估

### ChatGPT 排程任務 — 不可行

跑在雲端沙箱，沒有本機檔案存取權，也沒有跨執行保存的檔案系統。定位是**通知**而非執行。
另有活躍任務數上限（Plus 5 個、Pro/Enterprise 15 個），每次觸發計入訊息額度。
連硬條件 1、2 都過不了。

### ChatGPT agent mode — 已下架

依公開資料已於 2026 年 8 月初移除，官方導向 ChatGPT Work、雲端瀏覽器與 Codex。
即使仍在，其虛擬機也是 session 結束即銷毀。

### ChatGPT Workspace Agents — 不適用

OpenAI 目前最接近的產品：可排程、有 code interpreter 與受限 terminal。但僅限
Business / Enterprise / Edu 方案；執行環境明確定位為 sandbox，不是能長期保存 160 MB
資料並自由安裝原生套件的機器；且預告改採 Codex 式用量計費 —— 跑越久、用越多工具越貴，
而本專案每天跑 10 分鐘、下載十幾份 PDF，正是最貴的那種負載。

### Grok Bot — 唯一理論可行，但不划算

提供帳號層級的**持久化雲端 VM**，有檔案系統、終端機、瀏覽器，可安裝套件，檔案跨 session 保留。
架構上真的能跑。但：

- **US$200/月。** 同樣的錢租 VPS 可以租五年還有找。
- **官方標示 early beta**，可靠性、延遲、失敗復原均未經驗證；有「撞到週用量上限後卡在任務中間」的實測回報。
- **無法自行檢視、匯出或刪除記憶與檔案。** 唯一的累積資產會躺在拿不回來的地方。
- **中間多一層 LLM。** 需求是「每天 09:00 執行 `main.py`」，得到的是「每天 09:00 有個 AI
  讀懂你的意思再去執行」。只增加失敗模式，不帶來好處。
- 仍需手動完成 Heptabase OAuth，沒有省掉。

### 共同的根本錯配

這個專案**已經是一支寫好的確定性程式**。AI 工作流程平台的價值在於處理「沒有 API、
需要判斷、每次都不太一樣」的任務。把一支只需要排程器就能跑的程式交給 LLM 代跑，
是用最貴、最不確定的方式解決一個已經解決的問題。

## 四、Windows 移植 — 採用方案

整個 codebase 沒有 shell script、plist、`os.system`、unix 工具呼叫、`fcntl` 檔案鎖、
signal handler 或 symlink，路徑幾乎全走 `pathlib`。實際需要處理的只有三處：

| # | 問題 | 處理 |
| --- | --- | --- |
| 1 | `heptabase_keychain` 硬性拒絕非 macOS | `_load_backend()` 依平台指名後端（macOS 鑰匙圈／Windows 認證管理員），維持拒絕明文降級 |
| 2 | **相對路徑以 cwd 為基準** | `main.py`、`backfill.py` 啟動時 `os.chdir(ROOT)` |
| 3 | 主控台中文編碼 | `scripts/run_daily.bat` 設 `PYTHONUTF8=1` |

第 2 項最危險，因為它**默默失敗**：排程器用預設工作目錄時，程式會在那裡建立一個全新的
空候選池，推薦出無意義的結果卻完全不報錯。

第 3 項次危險：檔案 I/O 各處都有明確的 `encoding="utf-8"`，但排程非互動執行時 `sys.stdout`
會退回 cp950，論文標題含代碼頁外字元就會中斷整場執行。

不需修改 `src/zotero_arxiv_daily/`（上游複本）：`arxiv_retriever` 的 multiprocessing
已寫成 fork 不可用時退回 spawn，兩個 worker 都是模組層級函式、參數皆為字串，可 pickle。
代價是每次 spawn 要重新 import，每天多約 1–2 分鐘。

## 五、若日後不想依賴本機開機

正確的替代品不是 AI 平台，而是：

- **GitHub Actions 排程工作流程（免費）**：`.env` 放 Secrets，160 MB 走 Actions cache
  （單一 repo 上限 10 GB，7 天未使用才淘汰）。但 cache 不可原地更新，每天要用新 key 寫回，
  等於每天上下傳 160 MB。可行但繁瑣。
- **小型 VPS（約 US$5/月）**：一台永遠開機的 Linux，`cron` 一行搞定，資料庫放本機磁碟。
  比 Grok Bot 便宜約 40 倍且完全確定。

兩者的 Heptabase 匯出都仍需在有瀏覽器的機器上手動執行。
